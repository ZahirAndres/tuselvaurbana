Parte I

Documento de Inicio de Proyecto (PID)

1.1 Visión y Contexto del Negocio

🔍 Problema a Resolver

Existe una desconexión en el mercado tradicional de venta de plantas: el cliente adquiere una planta pero carece de la orientación y comunidad necesarias para mantenerla viva, lo que resulta en una experiencia frustrantemente corta y negativa.

💡 Propósito de la Plataforma

"Tu Selva Urbana" resuelve esto unificando el E-commerce con un ecosistema social e Inteligencia Artificial. No solo vende plantas, sino que acompaña al usuario con un Quiz de Diagnóstico para compras inteligentes, un Asistente Botánico con IA para cuidados, y un Feed Social para fomentar el sentido de pertenencia.

👥 Usuario Final

Entusiastas de la botánica en dos segmentos: principiantes ("plant killers") que necesitan guía de IA y recomendaciones personalizadas, y coleccionistas avanzados que buscan un catálogo especializado y una comunidad activa para compartir logros.

📈 Importancia Estratégica

Aumenta la retención y fidelización del cliente al transformar una compra transaccional en una experiencia continua, reduciendo la tasa de abandono post-compra y generando comunidad activa alrededor de la marca.

1.2 Glosario de Términos

OTP — One-Time Password
Código de verificación dinámico de 6 dígitos enviado por Email y SMS para validar la identidad del usuario antes de completar su registro final en la plataforma.
PendingRegistration
Estado transitorio en base de datos donde se almacena temporalmente a un usuario hasta que valide su identidad mediante el código OTP, actuando como buffer de seguridad.
Adoptar
Terminología de negocio propia de la plataforma para referirse a la compra o adquisición de una planta. Refuerza el vínculo emocional entre el cliente y su nueva planta.
Quiz de Diagnóstico
Algoritmo de filtrado basado en variables de entorno del usuario (luz disponible, presencia de mascotas) para sugerir plantas específicas. Incluye Sansevieria como fallback universal.
Asistente Botánico / Scanner IA
Módulo integrado con Google Generative AI (Gemini) que resuelve dudas de cuidado en lenguaje natural, delimitado por un System Prompt estricto al dominio botánico y del e-commerce.
JWT — JSON Web Token
Estándar de autenticación stateless firmado criptográficamente. Permite que el servidor valide la identidad del usuario sin necesidad de mantener sesiones activas en memoria.

1.3 Historias de Usuario — Product Backlog Inicial

👤 Cliente Nuevo
Como cliente nuevo, quiero registrarme mediante validación de dos factores (Email OTP y SMS) para garantizar la seguridad y autenticidad de mi cuenta.
✔ Definition of Done
  • Datos guardados en tabla PendingRegistration durante el proceso de verificación.
  • Email y SMS enviados correctamente mediante integración con Brevo (SMTP) y Twilio (SMS).
  • Al verificar el OTP, el usuario migra a la tabla User y se genera un JWT firmado con expiración definida.
🌿 Comprador Inexperto
Como comprador inexperto, quiero realizar un test de diagnóstico para que el sistema me recomiende la planta ideal para mi hogar y estilo de vida.
✔ Definition of Done
  • Formulario de variables ambientales (nivel de luz, presencia de mascotas) correctamente procesado en backend.
  • El sistema consulta la base de datos y retorna el Top 3 de plantas compatibles según los parámetros ingresados.
  • Mecanismo de fallback implementado (Sansevieria) cuando la consulta retorna 0 resultados compatibles.
🤖 Miembro de la Comunidad
Como miembro de la comunidad, quiero consultar a un asistente de Inteligencia Artificial para recibir consejos personalizados sobre el riego y cuidado de mis plantas.
✔ Definition of Done
  • Endpoint /api/chat conectado y funcional con la API de Gemini 2.5 Flash de Google.
  • System Prompt inyectado correctamente para delimitar las respuestas al dominio botánico y de la tienda.
  • Respuestas en lenguaje natural con latencia aceptable dentro de los límites del plan gratuito de la API.
🛡️ Administrador
Como administrador, quiero acceder a un panel de control protegido para visualizar estadísticas, gestionar el catálogo de plantas, aprobar pedidos y moderar usuarios de la comunidad.
✔ Definition of Done
  • Middleware isAdmin operativo, bloqueando acceso a rutas protegidas para usuarios no autorizados.
  • Componentes React renderizando métricas dinámicas en tiempo real (ingresos, usuarios activos).
  • CRUD completo para catálogo de plantas, pedidos y gestión de usuarios mediante peticiones autenticadas vía adminAPI.

1.4 Objetivos y Restricciones

🏁 Hito Principal (MVP): Lanzamiento del e-commerce funcional con pasarela de compra completa, integración de IA (Asistente Botánico / Chatbot) y flujo de registro seguro con doble validación OTP.

⚙️
Restricción de Backend Stateless: El servidor debe funcionar de forma stateless para permitir su despliegue y replicación horizontal en entornos PaaS modernos como Railway, sin pérdida de sesiones entre instancias.
🔌
Límites de Capa Gratuita: Las integraciones de terceros operan bajo restricciones de cuota: Brevo para SMTP, Twilio para SMS y Google Gemini para IA. El diseño debe contemplar manejo de errores por límite de llamadas.
🔐
Seguridad Obligatoria: Encriptación de contraseñas con Bcrypt (salt rounds: 10) y autenticación mediante JWT con tiempo de expiración definido. Protección contra inyección SQL garantizada por el ORM Prisma.
📝
Validación de Inputs: Filtrado estricto de todas las entradas del usuario en el backend mediante express-validator, previniendo inyección de datos maliciosos en todos los endpoints expuestos.
Parte II

Documento de Arquitectura de Software (SAD)

2.1 Introducción y Objetivos

🎯 Objetivo Técnico Principal

Crear una plataforma API-first, reactiva y escalable para la comercialización de plantas, que integre un ecosistema social activo y asistencia botánica automatizada basada en Inteligencia Artificial, garantizando una experiencia de usuario continua y de alta calidad tanto en el proceso de compra como en la post-venta.

La arquitectura seleccionada prioriza la escalabilidad horizontal, la separación de responsabilidades mediante el patrón MVC y la resiliencia ante los límites de las APIs de terceros. El sistema está diseñado para ser desplegado en entornos PaaS sin configuración de infraestructura compleja, facilitando el mantenimiento y los ciclos de entrega continua (CI/CD).

2.2 Requerimientos No Funcionales — Atributos de Calidad

📈
Escalabilidad
  • Arquitectura Stateless basada en tokens JWT.
  • El servidor Node.js/Express puede replicarse horizontalmente sin perder sesiones entre instancias.
  • Diseño modular que permite extraer módulos como microservicios en el futuro.
🔐
Seguridad
  • Autenticación: JWT firmados con secreto de servidor.
  • Cifrado en reposo: Contraseñas hasheadas con Bcrypt (salt: 10).
  • Validación: express-validator en todos los endpoints de entrada.
  • Anti-injection: ORM Prisma bloquea SQL injection automáticamente.
🛠️
Mantenibilidad
  • Backend desacoplado con patrón MVC: Routes → Controllers → Services.
  • Frontend basado en Componentes Funcionales modulares con React.
  • GlobalContext para manejo centralizado del estado de la aplicación.
⚡
Rendimiento
  • Node.js con modelo asíncrono I/O no bloqueante para peticiones concurrentes.
  • Gemini 2.5 Flash seleccionado por su baja latencia en generación de texto.
  • Vite en frontend para builds optimizados y Hot Module Replacement.

2.3 Vista Lógica — Arquitectura de Alto Nivel

El sistema implementa un Patrón Arquitectónico Cliente-Servidor, con un Monolito Modular en el backend y una Single Page Application (SPA) en el frontend. Las cuatro capas se comunican de forma desacoplada, permitiendo que cada capa sea modificada o escalada de forma independiente.

🖥️
Capa de Presentación — Frontend
SPA en React (Vite) con react-router-dom para enrutamiento interno y GlobalContext para estado global. Se comunica exclusivamente mediante api.js de forma asíncrona (fetch/axios).
▼
⚙️
Capa de Lógica de Negocio — Backend
Servidor Express.js que expone una API RESTful estructurada en módulos independientes: Auth · Plants · Orders · Users · Chat · Admin. Implementa el patrón MVC con middleware de autenticación y autorización.
▼
🔌
Capa de Integraciones — Servicios Externos
El backend actúa como orquestador conectando a APIs de terceros: Brevo (Email/SMTP) · Twilio (SMS/OTP) · Google Generative AI (Gemini LLM).
▼
🗄️
Capa de Persistencia — Base de Datos
PostgreSQL gestionado mediante Prisma ORM, garantizando integridad referencial con eliminaciones en cascada (onDelete: Cascade) y validación de tipos en tiempo de desarrollo.

Flujo de datos típico: El usuario interactúa con la SPA → la capa de servicios (api.js) envía una petición HTTP al endpoint del backend → el controlador del módulo correspondiente procesa la lógica, consulta la base de datos vía Prisma o llama a un servicio externo → devuelve la respuesta JSON al frontend → React actualiza el estado y re-renderiza la vista.

Parte III

Justificación de la Metodología

3.1 Metodología Seleccionada: Scrum (Enfoque Ágil)

Para este proyecto se ha seleccionado la metodología Scrum (Enfoque Ágil) debido a que la naturaleza de sus requisitos es evolutiva e innovadora, especialmente por la integración constante de componentes de Inteligencia Artificial (Prompt Engineering, Diagnóstico algorítmico) y flujos de experiencia de usuario complejos (E-commerce + Social Feed).

🔄
Flexibilidad Adaptativa
Sprints iterativos permiten ajustar los módulos de IA y UX según el feedback real de los usuarios en cada ciclo de entrega.
🧪
Pruebas Continuas
Validación en cada Sprint: flujos OTP, panel Admin, Quiz de Diagnóstico y respuestas del Asistente Botánico son probados de forma incremental.
📊
Gestión Visual
Product Backlog gestionado en Trello / GitHub Projects para transparencia en asignación de roles y seguimiento del progreso del equipo Full-Stack.
⚠️
Mitigación de Riesgo
Nivel de incertidumbre medio-alto en el desarrollo algorítmico de IA. Scrum permite pivotar rápido ante resultados inesperados en el Quiz o el Chatbot.
🚀
Entregas Iterativas
Cada Sprint entrega un incremento funcional del MVP, priorizando el E-commerce core sobre funcionalidades sociales secundarias.
🤝
Alineación de Equipo
Daily stand-ups, Sprint Reviews y Retrospectivas garantizan comunicación fluida y detección temprana de bloqueos técnicos.
Parte IV

Formato de Entrega — GitHub Pages

4.1 Instrucciones de Despliegue de Documentación

Para cumplir con el requisito de documentación moderna, colaborativa y accesible públicamente, la entrega del PID y el SAD se realizará a través de GitHub Pages. A continuación se detalla la estructura recomendada:

01
Un solo repositorio por equipo
Todo el equipo trabajará sobre el mismo repositorio Git. Este archivo index.html se coloca en la raíz o dentro de una carpeta docs/ del repositorio principal del proyecto.
02
Formato web activo
Los documentos PID y SAD están maquetados en este archivo HTML/CSS. Alternativamente, pueden usarse generadores como Jekyll, Hugo o Docsify para renderizar archivos .md con menú lateral navegable.
03
Activar GitHub Pages
En la configuración del repositorio: Settings → Pages → Source → Deploy from a branch → Main → /docs. Tras unos minutos, la documentación estará disponible en https://[usuario].github.io/[repositorio].
04
Estructura de carpetas recomendada
docs/ → Contiene index.html (este documento).
src/ → Código fuente del proyecto (frontend + backend).
README.md → Enlace directo a la GitHub Pages URL para acceso rápido.
